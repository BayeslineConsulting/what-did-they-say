# Conference Coding

Deliver the same study every six months: one coding workbook, one findings doc (with episode notes), and an updated trend dashboard. The design is inductive-first against a persistent instrument: the **master codebook** carries codes and categories across conferences so trends are comparable, while **themes are re-derived each run** as claims about that conference.

Read `references/protocol.md` before coding (rules for units, codes, the hybrid codebook, themes). Read `references/deliverables.md` before writing the doc, notes, or dashboard, and `references/methodology.md` before writing the methodology section (always the last section). Open `references/theory-dictionary.md` only at the theory-mapping step.

## Inputs to ask for (one message, all optional except transcripts)
1. Session transcripts (diarized ASR `.txt` like `Name (MM:SS.mmm)` blocks, or official talk text).
2. The previous run's `conference-YYYY-MM-coding.xlsx` **or** `history.json` + `master_codebook.json`. Without them, start from `assets/master_codebook.json` (seeded October 2026) and an empty history.
3. The dashboard link from the last run, so it is updated in place rather than duplicated.
4. Theme count (default 10, the series standard).

If a prior workbook is uploaded, recover state with `python scripts/state_from_workbook.py prior.xlsx RUN_DIR` (writes `master_codebook.json` and `history.json`).

## Workflow (RUN_DIR = /home/claude/run-YYYY-MM)

1. **Segment.** `python scripts/segment.py propose s1.txt s2.txt ...` lists conducting announcements, talk starts, and "Amen" endings. Write `RUN_DIR/manifest.json` (format: `references/manifest-example.json`) with each talk's start timestamp, speaker, calling, and name confidence. ASR garbles names: identify speakers from announcements plus talk content and mark low-confidence names "(as transcribed)". Then `python scripts/segment.py build RUN_DIR/manifest.json RUN_DIR/segs.json` and check every talk's last unit ends at its testimony.
2. **Metrics.** `python scripts/metrics.py RUN_DIR/segs.json RUN_DIR/metrics.json` — words, Christ-reference density, invitations, questions, leader mentions (via `references/aliases.json`; add new leaders and ASR variants there), recurring phrases.
3. **First-cycle coding.** Read every talk in full. Write `RUN_DIR/assign.txt` (range lines `T05.08-10 LOS HON`, ≤3 code keys per unit, every unit coded). Reuse master codes first; genuinely new codes go in `RUN_DIR/new_codes.json` with definition and include/exclude rules. Write a 2–3 sentence memo per talk into `RUN_DIR/memos.json`. Do not open the theory dictionary yet.
4. **Scripture.** Record references per talk in `RUN_DIR/scripture_refs.txt` (`T01|Job 38:7;D&C 76`). ASR rarely speaks chapter and verse, so identify quoted and retold passages from the text; when the official talk pages with footnotes are online, fetch them and reconcile. Mark the run's scripture counts approximate unless reconciled.
5. **Second cycle.** Group categories into themes stated as claims in `RUN_DIR/themes.json` (each theme lists its categories; `rhetoric_category` stays out of themes). Constant comparison: re-read the excerpts already in a category before adding to it.
5b. **Action list.** `python scripts/actions.py RUN_DIR/segs.json > candidates.txt`, then read every talk's directive passages too (list-style counsel like "First, … Second, …" is easy to miss). Curate `RUN_DIR/actions.json`: `[[theme_id, plain-language action, unit_id, verbatim quote], ...]`. Include everything that applies to members generally, from every speaker; flag subgroup items in the action text; exclude promises.
5b-2. **Bundle the list (series rule).** Turn actions.json into `RUN_DIR/bundles.json` (format: `references/example-run-2026-10/bundles.json`). Always start with the President of the Church: `oaks_own` = his own invitations this conference (read both of his talks in full; key name `oaks_own` regardless of who the president is, and set `president` to his name), with other speakers who gave the same challenge added as `echo` quotes; `oaks_repeated` = his earlier invitations that other speakers quoted this weekend. Then `others`: one bundle per distinct challenge, merging every speaker who gave a similar challenge into one item; ordered by number of speakers. Mark subgroup items with `audience`. Every action in actions.json must land in some bundle (verify_quotes.py checks this).
5c. **Theme examples.** Curate `RUN_DIR/examples.txt` (`TH01|KEY|T05.10|verbatim excerpt`): 8–10 per theme spread across its categories and talks, each a unit that actually carries that code, each excerpt long enough to make sense alone. Write `RUN_DIR/names.json` (talk → short display name, `*` for names as transcribed).
5d. **Verify.** `python scripts/verify_quotes.py RUN_DIR` must report zero failures before anything is written to the doc. Then `python scripts/render_sections.py RUN_DIR MASTER.json OUT_DIR` produces the action-list markdown and example tables.
6. **Build.** `python scripts/build_workbook.py RUN_DIR MASTER.json HISTORY.json|none OUT_DIR`, then `python /mnt/skills/public/xlsx/scripts/recalc.py OUT_DIR/conference-*-coding.xlsx 240`. Never ship with formula errors. The build fails loudly on uncoded units, unknown codes, or categories without a theme — fix and rerun. It also writes the updated `master_codebook.json` and `history.json` to OUT_DIR.
7. **Verify excerpts.** Every quotation used anywhere must be found verbatim in `segs.json` (grep it) with its unit ID and block timestamp.
8. **Theory mapping.** Map categories to constructs (Theory of Trying, UTAUT, Effective Use) or mark `novel`; rate the run on Painter et al.'s continuum. Update the category entries in `new_codes.json["categories"]` or note changes in the doc.
9. **Quality loop.** Run the critique passes in `references/deliverables.md` (verifier, skeptical academic, member, editor, chart reviewer). Export the doc to markdown and run `verify_quotes.py RUN_DIR doc.md`.
10. **Deliver** per `references/deliverables.md`: the findings doc (Claude Doc), episode notes as a section of it, the workbook and `master_codebook.json` + `history.json` via `present_files`, and the interactive report page: write `RUN_DIR/report_content.json` (theme notes, short labels, fun facts, speaker groups, scripture highlights, leaders, theory rows, methodology blocks; format in `references/example-run-2026-10/report_content.json`, every number traceable to the workbook), then `python scripts/build_report_page.py RUN_DIR OUT_DIR/master_codebook.json OUT_DIR/history.json /mnt/user-data/outputs/conference-trends.html`. Screenshot it at desktop and phone width, then publish with the Artifact tool, passing the prior page `url` so the series keeps one address. (`build_dashboard.py` is the older trends-only page.) For the public website: (1) write RUN/summaries.json (2-3 sentence summary per talk, written from a full reading; any quoted phrase must appear in the transcript), RUN/plan_ideas.json (2-3 small, practical ideas per invitation title, labeled on the site as suggestions, never as speakers' words), and RUN/links.json ({"T01": {"youtube": "ID", "church": "URL"}}; add only links verified on the official Church site or General Conference YouTube channel, never guessed). (2) Run build_report_page.py, which also writes OUT.json. (3) Run `python scripts/build_site.py OUT.json SITE_DIR https://DOMAIN` into the same site folder as earlier conferences so the archive grows. It writes tabbed pages per conference (Overview, Talks with per-talk pages and click-to-play video, Themes, Your Plan, By the Numbers, Methodology), plus About, archive, 404, sitemap, robots, og.png and vercel.json. (4) Upload SITE_DIR to the site's GitHub repository folder and deploy to Vercel. Sign-ups use assets/supabase_subscribers.sql (insert-only table) with site.signup_endpoint and site.signup_headers in report_content.json. The site name lives only in site.name.

## Guardrails
- Descriptive claims about this conference only; "concentrates in", never "drives".
- Single coder: always offer the blind double-code on the workbook's Reliability sheet.
- Never invent excerpts, counts, or scripture references; everything must come from the transcript as is. Flag uncertain attributions and do not assert intent or coordination the transcript cannot show.
- Keep themes as claims, not topics; keep the theme count the user set so the series stays comparable.
- Doctrinal content is reported as what speakers taught, not endorsed or disputed.

**Invitations are explicit only.** Count a sentence as something we were asked to do only when the speaker directly invites, urges, asks, pleads, calls upon ("I invite you", "let us", "please") or gives a direct instruction to listeners ("Keep your covenants"). Exclude statements, stories, "may we" wishes, "we should/can" descriptions, rhetorical "let us consider", and quotations of scripture or other leaders unless the speaker applies them to the listener. Scan every talk with the candidate patterns, review each sentence, and order bundles: the President of the Church's own invitations, then his earlier invitations explicitly repeated by other speakers, then all others by theme. Quotes may run across one transcript segment break; verify_quotes.py checks this.

**Themes are presented as patterns noticed, never as definitive.** Site copy says "themes we noticed", calls them lenses for pondering, and points to the talks as the source. The How It Works tab explains coding in plain language with one worked example whose passage and invitation are the same words.
